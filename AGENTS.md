# AGENTS.md — KONTAXPRO Desktop

## 1. Propósito

Este repositorio contiene **KONTAXPRO Desktop**, una aplicación de escritorio para pequeñas empresas y emprendedores de Ecuador.

Principio rector:

> **Robustez tributaria por dentro, simplicidad por fuera.**

Antes de modificar código, leer este archivo completo. Las decisiones aquí descritas son el diseño aprobado del proyecto y prevalecen sobre estructuras antiguas que aún existan en el código o en la base de datos de desarrollo.

# 3. Reglas generales obligatorias

1. No romper la separación por capas.
2. No acceder directamente a `KontaxDbContext` desde ViewModels.
3. No introducir lógica de negocio importante en code-behind.
4. Usar MVVM con CommunityToolkit.Mvvm.
5. Resolver dependencias con DI.
6. Los servicios EF deben preferir `IDbContextFactory<KontaxDbContext>` y contexto por operación.
7. Una operación transaccional compleja debe compartir el mismo contexto y la misma transacción.
8. Nunca usar `MAX(...) + 1` para secuenciales.
9. EF Core migrations + seeders son la fuente oficial de estructura e inicialización.
10. No usar scripts manuales de pgAdmin como mecanismo oficial de instalación.
11. No mantener el diseño antiguo solo por compatibilidad si contradice este archivo.
12. No agregar tablas/campos nuevos sin una inconsistencia funcional real.
13. Preferir `DeleteBehavior.Restrict` para maestros y operaciones históricas.
14. Operaciones confirmadas no se eliminan físicamente; se anulan/revierten.
15. Historiales append-only no se editan ni eliminan normalmente.
16. No reintroducir campos obsoletos listados al final de este documento.
17. Compilar entre bloques y no avanzar con build roto.

# 4. Reconstrucción total de la base de desarrollo

La base PostgreSQL actual es de desarrollo y será eliminada completamente cuando el modelo final esté implementado.

Objetivo:

```text
BD vacía
→ InitialCreate
→ StructuralSeeder
→ DemoSeeder (solo Development)
→ KONTAXPRO listo para iniciar sesión
```

La base actual no es la fuente de verdad. Las entidades + configuraciones EF Core son la fuente de verdad.

Antes de cualquier borrado:
- confirmar ambiente `Development`;
- identificar explícitamente host y nombre de base;
- abortar si hay cualquier indicio de Production.

La migración final debe ser una sola `InitialCreate` limpia, no una cadena de migraciones experimentales.

# 5. Seeders

## StructuralSeeder
Se ejecuta en todos los ambientes.

Contiene únicamente:
- catálogos estructurales;
- roles;
- permisos;
- relaciones rol-permiso;
- consumidor final;
- otros datos estructurales indispensables.

Debe ser idempotente.

## DemoSeeder
Solo `Development`.

Debe crear al menos:

### Usuario demo
- un usuario activo;
- contraseña creada con el `PasswordHasher` real;
- acceso a dos empresas;
- rol ADMINISTRADOR en ambas.

### Empresa Demo 1
- RUC ficticio de desarrollo;
- régimen;
- establecimiento 001 matriz;
- punto de emisión 001;
- bodega principal;
- caja principal;
- lista de precio base;
- configuración mínima;
- secuenciales mínimos;
- preferencias usuario/empresa.

### Empresa Demo 2
Lo mismo, con datos distintos.

Objetivo funcional:
1. Login.
2. Al pertenecer a 2 empresas, mostrar `SeleccionarEmpresaWindow`.
3. Poder entrar a cualquiera.
4. Poder cambiar de empresa.
5. Tener establecimiento/punto/bodega/caja mínimos para pruebas.

Nunca ejecutar DemoSeeder en Production.

# 6. Convenciones PostgreSQL

## IDs
- PK local: `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- UUID solo donde exista necesidad real de identidad portable/sincronización.

## Fechas
- `date`: fechas civiles/tributarias.
- `timestamp with time zone`: eventos exactos.
- Usar UTC cuando corresponda.

## Dinero
- `NUMERIC(18,2)`.

## Cantidades y costos
- `NUMERIC(18,6)`.

## Estado
Para maestros:
- `estado INTEGER`
- 1 = activo
- 0 = inactivo

Para workflows:
- códigos controlados por Domain/Application.

# 7. Multiempresa

KONTAXPRO es multiempresa y multiestablecimiento.

Reglas:
- aislamiento estricto;
- validar que relaciones pertenezcan a la misma empresa;
- usar integridad compuesta donde ayude;
- no confiar solo en filtros de UI.

Ejemplo:
`productos_presentaciones(producto_id, empresa_id)` debe poder validarse contra `productos(id, empresa_id)`.

# 8. Topología SERVIDOR / CLIENTE

Cada instalación tiene configuración local:

- `instalacion_id` UUID
- `tipo_instalacion`: `SERVIDOR` | `CLIENTE`
- host PostgreSQL
- puerto
- nombre BD
- directorio base
- última caja usada como preferencia
- cache de licencia
- último tiempo confiable
- secretos en almacenamiento seguro del SO

## SERVIDOR
Puede alojar:
- PostgreSQL;
- worker de facturación electrónica;
- certificado;
- XML;
- RIDE;
- backups;
- procesos programados.

## CLIENTE
- ejecuta KONTAXPRO Desktop;
- se conecta al PostgreSQL del servidor;
- no necesita BD local.

Una sucursal remota puede tener su propio servidor + PostgreSQL independiente.

# 9. Cajas compartidas

Una caja representa un **fondo físico**, no una computadora ni un usuario.

Una misma `caja_sesion` puede ser usada simultáneamente por varios usuarios y varios equipos.

`cajas_sesiones`:
- `abierta_por_usuario_id`
- `cerrada_por_usuario_id` nullable

Cada `movimientos_caja` guarda `usuario_id`.

Solo una sesión `ABIERTA` por caja.

`CurrentSession` puede mantener:
- `CajaId`
- `CajaNombre`
- `CajaSesionId`

Reglas:
- una sola caja abierta en el establecimiento → selección automática;
- varias → usuario elige;
- caja debe pertenecer al establecimiento activo;
- no existe relación fija equipo→caja;
- no existe relación fija usuario→caja.

1. inspeccionar código existente;
2. identificar archivos reutilizables;
3. eliminar/adaptar diseño obsoleto;
4. actualizar Domain;
5. actualizar Infrastructure;
6. adaptar Application cuando el nuevo modelo lo requiera;
7. adaptar Desktop solo cuando sea necesario para compilar/funcionar;
8. ejecutar build;
9. corregir errores;
10. no avanzar con build roto.

1. eliminar migraciones experimentales;
2. confirmar Development;
3. borrar BD de desarrollo;
4. generar `InitialCreate`;
5. aplicar migración;
